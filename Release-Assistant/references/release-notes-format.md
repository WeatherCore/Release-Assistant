# Release Notes 格式规范

生成 release notes 时按本文件执行。语言跟随项目 README 主语言。

## 标题惯例

```
v<版本> · <一句话主题>
```

主题从本批提交的主线提炼（如「双引擎加固与老格式兼容」「首个正式版」），不写日期（GitHub 页面自带时间）。

## 正文结构

```markdown
<一两句开场：这个版本是什么定位，一句话说清对用户的最大变化。>

## ✨ 新功能
- **<特性名>**（`<短hash>`）：<一句用户视角的价值说明，可带代码位置>

## 🔒 安全加固
- **<加固点>**（`<短hash>`）：<影响谁、防什么>   ← 有安全改动时必须单独成节，位置靠前

## 🐛 修复
- **<症状>**（`<短hash>`）：<修复后的行为>

## 📝 其他
- <docs/chore/deps 类，合并成短条目，不逐条罗列琐碎提交>

**Full Changelog**: https://github.com/<owner>/<repo>/compare/<prev-tag>...<new-tag>
```

## 分组与措辞规则

1. **用户视角优先**：条目写「用户能得到什么/不再遇到什么」，不写实现细节；实现位置可用反引号附在括号里（如 `src/render.ts`）。
2. **短 hash 必须真实**：每个引用的 hash 从 `git log --oneline <tag>..HEAD` 原样摘取，生成前逐一核对。
3. **feat 归新功能，fix 归修复**：一条提交同时含两者时按主要语义归组，跨组拆条允许。
4. **安全类置顶突出**：防 DNS rebinding、输入校验、权限类改动单独成节；如果这批只有安全修复，标题也可点明。
5. **其他类收敛**：docs/chore/deps 合并概括（如「移除未使用的 pdfjs-dist 依赖」），不逐条复读 commit message。
6. **首次发版**：开场一句定位 + 按「转换引擎/导出/体验」等特性域分组写全量特性，不再按 hash 分节；结尾附使用方式（在线/本地）。
7. **compare 链接**：prev tag 是上一个发行 tag，next 是本次新 tag；首次发版用 `/commits/<tag>` 形式。

## 网页表单填写指引（随 notes 一并给用户）

- **Tag**：本地 tag 先行 → 下拉选已有 tag；否则输入新 tag 名选 create new tag，目标 = 主分支。
- **Release label**：正式版「无」；预览/实验版「预发行版」。
- **附件区**：Web 应用留空；CLI/库类项目如需附产物再议。
- **「包」区**：应用类项目跳过。
